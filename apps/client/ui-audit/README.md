# UI-Audit toolkit

Gives a sweep/tester agent (especially a multimodal one, e.g. Fable) **eyes** on the renderer
instead of only reading source: it loads a prepared save into the real app, clicks through every
page, screenshots each one, and runs a few cheap automated consistency checks. This directory is
entirely tooling — nothing in here ships in the packaged game (see "How it stays out of prod" below).

## Quick start

From `apps/client/`:

```
pnpm ui-audit:fixtures   # (re)generate the two fixture saves — only needed after big content changes
pnpm ui-audit            # run the full tour: starts a dev server, screenshots everything, writes report.md
```

`ui-audit` takes care of the dev server itself (starts it, waits for it, tears it down after) — you
don't need `pnpm dev` running first. It takes roughly 20-30s for 2 fixtures × 27 pages.

**Then, as a sweep agent: open the screenshots and actually look at them.** The report tells you
*where* to look; it can't tell you whether something looks wrong. Start with
`ui-audit/shots/<fixture>/<page>.png`, cross-reference `report.md` for that page/fixture.

## What you get

- `ui-audit/shots/<fixture>/<page>.png` — one full-page (1920×1080 viewport, full scroll height)
  screenshot per page, per fixture. Filenames are the page id (`combat.png`, `mining.png`,
  `character.png`, ...) — deterministic, overwritten fresh on every run (stale shots from a
  previous run are deleted first).
- `ui-audit/report.md` — automated findings (see below) + a screenshot index. Regenerated fully on
  every run (don't hand-edit it).

## The two fixtures

Generated by `gen-fixtures.mjs` (content-driven — it filters the live `@hearthforge/content`
catalog by type/slot/value rather than hardcoding item IDs, so it keeps working as content
changes):

- **midgame** — "Mira Ashfall", combat level ~30, mixed/mid-tier gear across every equip slot,
  varied gathering-skill levels, an active mining action in progress, a couple of timed buffs, a
  handful of monster kills / achievements / mastery entries, no pets. Good for "early/mid-game
  screen density" checks.
- **endgame** — "Korveth Grimhollow", combat level ~92, nearly full high-tier gear, several
  skills at 99, 7 pets (with a companion equipped), 24 achievements, a much fuller inventory/bank.
  Good for "does this layout hold up when every field is populated" checks (long names, big
  numbers, full grids).

Both are seasoned characters with the onboarding guide already completed (see "Gotchas" below) —
the tour lands directly on `CHARAKTER`/`KAMPF` etc., no menu/character-creation/tutorial clicking.

Fixture JSON lives in two places (both written by `gen-fixtures.mjs`, always in sync — just rerun
the script, don't hand-edit either):

- `apps/client/ui-audit/fixtures/<name>.json` — canonical, the one to open if you want to read/diff
  the actual GameState (e.g. to see exactly which gear got equipped).
- `apps/client/src/renderer/public/ui-audit-fixtures/<name>.json` — a served copy. Vite's default
  `publicDir` is `src/renderer/public`, so this is reachable at `/ui-audit-fixtures/<name>.json`
  with zero dev-server config changes. This is the one the running app actually fetches.

## How the fixture hook works (renderer side)

`src/renderer/game/fixtureLoader.ts` + a `useEffect` in `GameContext.tsx`: if the URL has
`?fixture=<name>` (and only in a dev build — see below), it fetches
`/ui-audit-fixtures/<name>.json`, runs it through the real persistence `deserialize()` path (same
sanitize/migrate pass a real save gets — no special-cased "test mode" state shape), and jumps
straight to `MainLayout` with `activeSlotRef = null` (so autosave/"Save"/"Main Menu" never write
over a real save slot).

Deserialize is called with `now = summary.savedAt` (same trick `importSave` uses), **not**
`Date.now()`. This matters: without it, `deserialize`'s offline-catchup simulation would run for
however long has passed since the fixture was *generated* (could be hours/days), silently drifting
skill XP/inventory/achievements on every tour run depending on wall-clock timing. With it, the
fixture loads bit-for-bit identical every time — that's what makes the screenshots deterministic.

**How it stays out of production:** every check in `fixtureLoader.ts` is gated on
`import.meta.env.DEV`, which Vite inlines to the literal `false` in a production build; the dead
`if (import.meta.env.DEV)` branches (fetch call included) get stripped by the build minifier. Verified:
`grep -c ui-audit-fixtures out/renderer/assets/*.js` is `0` after `pnpm build`. The one thing that
*does* end up in a full `pnpm build` output is the static fixture JSON itself (Vite copies
`publicDir` unconditionally) — a few KB of inert data nothing fetches outside a dev build, not a
reachable code path. If that ever needs to be trimmed for packaging, exclude
`out/renderer/ui-audit-fixtures/` in `electron-builder.json`.

## Automated checks (what's in report.md)

Run once per page visit, results grouped into `report.md`:

- **Raw i18n tokens** — visible text matching `/^[a-z][a-z0-9]*(\.[a-z][a-z0-9]*){1,}$/`, i.e. text
  that looks like `some.key.path` instead of a translated string (a missing `t()`/`tr()` call, or a
  translation key that's missing from `translations.ts`).
- **Broken images** — `<img>` with `naturalWidth === 0` after load.
- **Overflow / clipped text** — elements where `scrollWidth` exceeds `clientWidth` by >12px, split
  into three buckets by computed style so intentional ellipsis truncation doesn't drown out real
  bugs:
  - *spillover* (`overflow: visible`) — content likely visibly pokes outside its box. Look at these
    first; on the first tour run this caught a real bug (see below).
  - *hard-clip* (`overflow: hidden`, no `text-overflow: ellipsis`) — text silently cut off with no
    visual indication there's more.
  - *ellipsis* — `overflow:hidden; text-overflow:ellipsis` — graceful, by design, informational only.
- **Console errors/warnings/pageerrors** — collected via Playwright's `page.on('console'|'pageerror')`
  for the whole session, tagged with the page that was active when they fired.
- **Font-family drift** — computed `font-family` of every text-bearing element, first font in the
  stack, checked against the whitelist declared at the top of `tour.mjs` (kept in sync with the
  `@font-face` rules + fallback chain in `styles/base.css`). If you add a font to `base.css`, add it
  to `FONT_WHITELIST` in `tour.mjs` too, or every page will show false positives.
  found on a run.
- **Button class census** (informational, not pass/fail) — counts `<button>` elements per page with
  vs. without a "Citadel" class (`ds-button`/`citadel`/`hf-btn` substring). The Citadel look is
  being rolled out gradually across the app (see project memory: "Sidebar-Stil = Design-System"),
  so a high "other" count on an unmigrated page is expected, not automatically a bug — use this to
  see *where* the rollout hasn't reached yet, not as a checklist to zero out.
- **Emoji-fallback count** (informational) — elements matching `[class*='fallback']` (the pattern
  this codebase uses for "no PNG art yet, showing the emoji" — see `ItemCell`/`getSidebarIcon`
  callers). Tells you roughly how much placeholder art remains on a page; not itself a bug.

None of these checks touch game *logic* — they're purely DOM/CSS inspection. They can't tell you
"this number is wrong" or "this button does the wrong thing" — that's still a job for the
screenshots + a human/multimodal read, or for the engine's own test suite.

## Known finding from the first run (2026-07-02)

The very first tour run flagged `span.ach2-name` on the Achievements page as "spillover" on every
achievement card. Looking at the screenshot: the achievement title text genuinely overlaps the
rarity badge pill in the top-right of the card (e.g. "GewöhnlichLehrling" running together). Real
CSS bug in `AchievementsPage`/`pages.css` (`.ach2-name` vs. the rarity badge), not fixed as part of
building this tool — flagged for a follow-up UI pass.

## Gotchas / design notes for whoever touches this next

- **Onboarding guide must stay off in fixtures.** `createGame()` defaults every new save to
  `onboarding: { active: true, step: 0 }`, and while active `OnboardingGuide` makes *only* the
  currently-spotlighted element clickable (see its own header comment) — that would make the tour
  unable to click anything else. `gen-fixtures.mjs` explicitly sets
  `state.onboarding = legacyOnboarding()` (the engine's own "already completed" state, same as any
  pre-guide save) right after `createGame()`. If you add a third fixture, don't forget this line.
- **Achievement-unlock toasts on first render.** `components/Toasts.tsx` diffs `state.achievements`
  against an empty baseline on mount, so a fixture that "arrives" with achievements already unlocked
  triggers a toast for each of them (4s duration, `TOAST_MS` in `Toasts.tsx`). `tour.mjs` waits
  ~4.2s after the initial fixture load before screenshotting anything so these clear first. Not a
  bug, just fixture-load-specific noise — don't be surprised if you see it while iterating manually.
- **The 2nd ring vanishes on load — this is a real, separate persistence bug, not a fixture-script
  bug.** `packages/persistence` `sanitizeState` nulls any equipment slot where
  `content.items[id].slot !== slot`; every ring declares its canonical slot as `"ring1"`, so the
  *legitimate* 2nd ring sitting in the `"ring2"` slot fails that check and gets wiped on the very
  next `deserialize` (app restart / slot load / this fixture hook). `gen-fixtures.mjs` still
  equips a 2nd ring (harmless, and it'll "just work" once that's fixed) — don't be surprised the
  served fixture only shows one ring. This is `packages/**` territory (logic-dev), not something
  this UI tool should patch around; flag it to the CEO if it's still unfixed.
- **Why a standalone `vite.tour.config.mjs` instead of `electron.vite.config.ts`:** the latter is an
  `electron-vite` multi-target config (main/preload/renderer) that launches the actual Electron app.
  ui-dev agents in this repo don't run Electron interactively. The renderer is a normal React SPA —
  every `window.hearthforge?.*` bridge call is optional-chained with a browser fallback (see
  `src/renderer/saves.ts`) — so it runs fine standalone under plain `vite` + Playwright's headless
  Chromium. `vite.tour.config.mjs` mirrors just the `renderer` block (root + react plugin +
  `__APP_VERSION__` define).
- **Playwright browser binaries** are a one-time local install, not part of `pnpm install`:
  `pnpm --filter @hearthforge/client exec playwright install chromium` (~180MB download). If
  `pnpm ui-audit` fails with a "browser not found" error, run that first.
- **Not wired into `pnpm test`.** This is opt-in and slow-ish (dev server boot + 54 page visits +
  screenshots take ~20-30s) — it's a manual/sweep-agent tool, not a CI gate.
- If you add a new sidebar or topbar page in `navigation.ts`, you don't need to touch `tour.mjs` —
  it discovers pages at runtime via the `data-guide-id="sidebar.*"`/`"topbar.*"` markers that
  `Sidebar.tsx`/`TopBar.tsx` already put on every nav button.
